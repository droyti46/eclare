# CLAUDE.md

Этот репозиторий — исследовательский код.

Главные цели:

1. быстро проводить эксперименты;
2. сохранять простоту кода;
3. не терять воспроизводимость;
4. не допускать скрытых методологических изменений;
5. оставлять исследователю полный контроль над решениями.

Если есть выбор между сложным и простым решением — выбирай простое.

---

# Основной принцип

Код должен помогать понимать эксперимент, а не скрывать его.

Предпочитай:

- простой и прямой код;
- явный поток данных;
- небольшие изменения;
- явные конфиги;
- воспроизводимые эксперименты;
- минимальное количество абстракций.

Избегай:

- архитектуры «на будущее»;
- лишних wrapper/factory/registry;
- ненужных классов;
- скрытых defaults;
- больших рефакторингов без необходимости.

Не создавай функцию на 1–2 строки, если она используется один раз и не улучшает читаемость.

Не создавай класс, если достаточно функции.

Не обобщай решение, пока нет хотя бы нескольких реальных use-case.

---

# Не делай лишнего

Выполняй именно поставленную задачу.

Без явной необходимости не:

- рефактори соседний код;
- переименовывай файлы;
- перестраивай архитектуру;
- меняй зависимости;
- меняй датасет;
- меняй split;
- меняй preprocessing;
- меняй модель;
- меняй seed;
- меняй метрики;
- меняй гиперпараметры;
- удаляй экспериментальные результаты;
- делай commit/push.

Если заметил проблему вне текущей задачи — сообщи о ней, но не исправляй молча.

---

# Перед изменением кода

Перед нетривиальной задачей сначала:

1. прочитай существующую реализацию;
2. посмотри соседний код;
3. найди конфиги;
4. посмотри тесты;
5. пойми, что должно измениться, а что должно остаться прежним.

Не начинай с создания новой архитектуры.

---

# Стиль кода

Код должен быть:

- коротким;
- явным;
- читаемым;
- предсказуемым.

Предпочитай хорошие названия и локальные переменные комментариям.

Комментарии должны объяснять **почему**, а не пересказывать код.

Хороший комментарий:

```python
# Исключаем неоднозначные liftOver mappings,
# чтобы не добавлять сомнительные пары в validation.
```

Плохой комментарий:

```python
# Увеличиваем counter
counter += 1
```

Не добавляй defensive-код для невозможных сценариев.

Не скрывай ошибки через:

- `except Exception`;
- произвольные retries;
- молчаливые fallback;
- автоматическое удаление проблемных строк.

Сначала найди причину проблемы.

---

# Минимальные изменения

Сохраняй существующее поведение, если пользователь не просил его менять.

Не смешивай в одном изменении:

- новый функционал;
- рефакторинг;
- форматирование;
- unrelated cleanup.

Если изменение можно сделать локально — делай локально.

---

# Научная методология

Корректность эксперимента важнее того, что код успешно запустился.

Для каждого существенного эксперимента нужно понимать:

### Вопрос
Что именно мы проверяем?

### Гипотеза
Какой результат её поддерживает?

### Изменяемый фактор
Что конкретно меняется?

### Контроль
Что остаётся неизменным?

Например:

- dataset;
- split;
- backbone;
- preprocessing;
- optimizer;
- learning rate;
- batch size;
- loss;
- seed;
- training budget;
- metrics.

Если одновременно меняется несколько важных факторов — обязательно предупреди, что интерпретация результата становится неоднозначной.

---

# Baseline

Перед интерпретацией результата всегда определяй baseline.

Нельзя говорить, что метод стал лучше, если сравниваемые эксперименты различаются по:

- данным;
- split;
- preprocessing;
- метрикам;
- training budget;
- checkpoint selection.

Если сравнение не полностью корректное — явно скажи почему.

---

# Гиперпараметры

Не позволяй важным параметрам исчезать внутри defaults.

Для training experiment проверь релевантные:

- learning rate;
- optimizer;
- weight decay;
- batch size;
- epochs / steps;
- scheduler;
- warmup;
- loss;
- temperature;
- sequence length;
- tokenizer;
- pooling;
- projection head;
- dropout;
- frozen/unfrozen layers;
- positive/negative ratio;
- seed.

Не нужно перечислять всё каждый раз.

Показывай только то, что влияет на текущий эксперимент.

Если параметр изменён, укажи:

- старое значение;
- новое значение;
- зачем его изменили;
- остаётся ли сравнение с baseline корректным.

---

# Запуск экспериментов

По возможности работай по этапам.

## 1. Проверка

Сначала проверь:

- пути;
- данные;
- размеры;
- конфиг;
- checkpoint;
- genome assembly;
- входные колонки.

## 2. Smoke test

Сначала минимальный запуск:

- несколько samples;
- один batch;
- один forward;
- один optimization step.

Проверь:

- shapes;
- loss;
- gradients;
- outputs.

## 3. Маленький эксперимент

Если full run дорогой — сначала небольшой subset или короткое обучение.

## 4. Полный эксперимент

Только после предыдущих проверок запускай полный эксперимент.

Не трать GPU, если проблему можно обнаружить за несколько секунд.

---

# Во время эксперимента

Exit code `0` не означает, что эксперимент корректный.

Проверяй:

- NaN / Inf;
- exploding loss;
- constant loss;
- zero gradients;
- collapsed embeddings;
- подозрительно идеальные метрики;
- пустые subsets;
- неожиданный размер датасета;
- неправильный checkpoint;
- неожиданно замороженные параметры;
- silent fallback.

---

# После эксперимента

После существенного эксперимента обязательно сообщи:

### Что проверяли

Коротко сформулируй вопрос.

### Setup

Датасет, модель, важные параметры, seed.

### Что изменилось

Точная разница относительно baseline.

### Результат

Основные метрики.

### Интерпретация

Что результат действительно позволяет утверждать.

### Ограничения

Confounders, шум, маленький dataset, возможная leakage и т.п.

### Следующий эксперимент

Предложи самый маленький эксперимент, который уменьшит основную неопределённость.

Но не запускай его автоматически без запроса.

---

# Воспроизводимость

Для важных запусков сохраняй или сообщай:

- command;
- config;
- seed;
- dataset version;
- filters;
- split;
- model/checkpoint;
- output directory;
- основные метрики.

Если эксперимент нельзя полностью воспроизвести — скажи, какой информации не хватает.

---

# Данные

Изменение датасета — это изменение эксперимента.

После фильтрации полезно проверять:

- исходное число элементов;
- число после фильтрации;
- positives;
- negatives;
- train;
- validation;
- test;
- unmapped / dropped examples.

Не удаляй неудобные данные молча.

Неожиданное изменение количества элементов — повод проверить pipeline.

---

# Data leakage

Активно проверяй возможную leakage.

Особенно:

- одинаковые элементы между split;
- пересекающиеся genomic intervals;
- одинаковые loci;
- orthologs между train и test;
- сильно похожие sequences;
- preprocessing, обученный на всех данных;
- подбор параметров по test set.

Если leakage возможна — предупреди до интерпретации результатов.

---

# Genomics

Никогда не смешивай молча:

- species;
- genome assemblies;
- chromosome naming;
- annotation versions;
- coordinate conventions.

Для genomic dataset должны быть понятны:

- species;
- assembly;
- source;
- координатная система.

Для BED-подобных файлов явно учитывай:

- 0-based или 1-based;
- half-open или closed intervals.

При извлечении sequence проверяй:

- длину;
- chromosome boundaries;
- strand;
- reverse complement;
- ambiguous bases.

---

# Cross-species mapping

Для межвидовых экспериментов mapping является частью методологии.

При создании пар фиксируй:

- source species;
- target species;
- assemblies;
- mapping method;
- направление;
- reciprocal mapping;
- one-to-many mappings;
- unmapped cases;
- ambiguous mappings.

Успешный `liftOver` сам по себе не доказывает биологическую ортологию.

---

# Negative sampling

Negative sampling может полностью определить сложность задачи.

Никогда не меняй его молча.

Указывай:

- что считается negative;
- откуда они берутся;
- exclusions;
- positive/negative ratio;
- matching по длине;
- matching по GC;
- другие matching criteria.

Проверяй, не может ли модель решить задачу через shortcut:

- GC;
- длину;
- chromosome;
- padding;
- dataset source;
- species-specific artifacts.

---

# Метрики

Метрика должна отвечать исследовательскому вопросу.

Не добавляй метрику просто потому, что она выглядит лучше.

Для retrieval experiment при необходимости показывай:

- precision@k;
- recall@k;
- MRR;
- enrichment;
- random baseline.

Не называй результат «хорошим» без точки сравнения.

---

# Seeds и статистика

Один seed подходит для:

- debugging;
- smoke tests;
- ранних exploratory experiments.

Если вывод зависит от небольшой разницы между моделями, одного seed обычно недостаточно.

Не перебирай seeds до получения красивого результата.

Не скрывай неудачные runs.

---

# Failed experiments

Различай:

**experiment failed technically**

и

**experiment completed and gave negative result**.

Это разные вещи.

Не удаляй отрицательные результаты из истории только потому, что они не подтверждают гипотезу.

---

# Не исправляй методологию молча

Если заметил сомнительное решение:

1. укажи проблему;
2. объясни, почему она важна;
3. предложи варианты;
4. не меняй постановку эксперимента без явного основания.

Исследователь принимает научные решения.

---

# Всегда сообщай о методологических изменениях

Нельзя спрятать внутри «cleanup» изменение:

- dataset;
- split;
- filtering;
- sampling;
- preprocessing;
- sequence length;
- model;
- checkpoint;
- optimizer;
- learning rate;
- loss;
- metric;
- seed;
- epochs;
- early stopping.

Это должно быть явно обозначено.

---

# После изменения кода

Для нетривиальной задачи кратко сообщи:

### Изменено
Что именно поменялось.

### Почему
Почему выбран этот вариант.

### Сохранено
Что намеренно осталось прежним.

### Проверено
Какие tests/commands действительно были запущены.

### Не проверено
Что осталось неопределённым.

Никогда не утверждай, что тест прошёл, если он не запускался.

# Git

Не делай commit без явного запроса.

Не делай push без явного запроса.

Не удаляй пользовательские изменения.

Перед редактированием файла с существующими изменениями проверь diff.

Сохраняй diff минимальным.

---

# Главное правило

Цель — не написать больше кода.

Цель — уменьшить неопределённость.

Каждое изменение должно делать эксперимент:

- возможным;
- корректным;
- понятным;
- воспроизводимым.

Каждый эксперимент должен отвечать на конкретный вопрос.

Каждый вывод должен следовать из полученных данных.

Если сомневаешься — выбирай более простое решение и явно обозначай неопределённость.
